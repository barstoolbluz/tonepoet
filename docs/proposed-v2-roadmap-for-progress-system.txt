For v2, I would treat this as a progress instrumentation subsystem, not another reporter patch. v1 makes the existing pipeline visible. v2 should make long-running work measured, alive, cancellable, and explainable across SACD, CUE, 7z, FLAC batches, and future routes.

Document #2 already frames these as follow-up subsystem items: ffmpeg/sox/archive progress parsing, heartbeat events, conservative ETA, confidence labeling, immediate cancellation visibility, and TUI changes beyond existing contracts.

V2 product goal

Users should see:

Converting track 1 of 2: So What · 67% of current track · elapsed 2m 14s

instead of:

20% Converting

The goal is not a smoother bar by itself. The goal is to show what is happening, whether the app is alive, and how trustworthy the percentage is.

Proposed v2 architecture

Add a route-neutral progress layer between long-running operations and the existing pipeline reporter:

child process / long operation
        ↓
ProgressProbe / OperationProgress
        ↓
PipelineEvent::Progress or richer internal progress event
        ↓
BroadcastReporter
        ↓
ProgressUpdate
        ↓
TUI

Core new concepts:

enum ProgressConfidence {
    Measured,    // parsed from tool output or byte/sample counters
    Estimated,   // duration/sample/item-weighted estimate
    Unknown,     // alive, but no meaningful denominator
}

enum ProgressScope {
    Overall,
    Stage,
    File,
    Track,
    Tool,
}

struct OperationProgress {
    scope: ProgressScope,
    confidence: ProgressConfidence,
    phase_progress: Option<f32>,
    file_progress: Option<f32>,
    message: String,
    elapsed: Duration,
}

This should stay route-neutral. SACD, CUE, 7z, and FLAC code should feed facts into the same progress layer rather than formatting special-case UI strings in each route.

Workstream	Purpose	Generalizes across routes?

Implementation plan
1. Add a progress instrumentation module

Add something like:

src/convert/pipeline/progress/
  mod.rs
  operation.rs
  throttle.rs
  heartbeat.rs
  confidence.rs
  tool_probe.rs

Responsibilities:

track elapsed time
format user-facing progress messages
throttle frequent updates
classify progress as measured, estimated, or unknown
emit PipelineEvent::Progress through the existing reporter
avoid route-specific logic

This module should expose small helpers:

OperationProgressTracker::new(stage, item_id, reporter)
OperationProgressTracker::start_unit(...)
OperationProgressTracker::measured(...)
OperationProgressTracker::estimated(...)
OperationProgressTracker::unknown_alive(...)
OperationProgressTracker::finish_unit(...)
OperationProgressTracker::cancel_requested(...)
2. Add throttling as shared infrastructure

V1 can emit sparse stage and track events without much throttling. V2 needs throttling because child-process parsers may emit frequently.

Suggested rule:

Send immediately when:

stage changes
message changes materially
cancellation begins
failure occurs
terminal state arrives

Otherwise send when:

progress changes by at least 0.5%, or
at least 500ms elapsed since the last emitted update

Heartbeats should use a slower cadence, such as 10–15 seconds.

3. Add elapsed-time support

Elapsed time should be measured by the operation tracker, not manually in every route.

Message rules:

under a short threshold: omit elapsed time
after the threshold: append elapsed time
use coarse formatting: 48s, 2m 14s, 1h 03m

Examples:

Extracting archive · elapsed 48s
Converting track 1 of 2: So What · elapsed 2m 14s
4. Add unknown-but-active heartbeats

For opaque operations, emit truthful progress:

Converting track 1 of 1 · still running
Converting track 1 of 1 · progress unavailable from sox
Extracting archive · still running

Do not advance percentages without a real basis. Keep the stage start percentage or the last known progress.

This directly addresses the SACD case where one track can take 162 seconds with no visible activity.

5. Add tool progress probes

Create adapters for child-process output. Keep each parser isolated and optional.

Potential probes:

src/convert/pipeline/progress/probes/ffmpeg.rs
src/convert/pipeline/progress/probes/sox.rs
src/convert/pipeline/progress/probes/archive.rs
ffmpeg

Parse progress from either:

-progress pipe:2 style key-value output, preferred
stderr time=... fallback

Progress basis:

current_time / expected_duration
sox

Only parse progress when sox emits usable position/progress output in the current invocation mode. Do not invent progress when sox gives no denominator.

Fallback:

progress unavailable from sox · still running
archive extraction

Prefer measured data:

extracted bytes / total bytes

Fallbacks:

extracted files / total files
current archive member name
unknown but active
6. Add conservative ETA

ETA should come after measured or estimated progress has enough history.

Rules:

no ETA during the first unit unless tool-level progress exists
use duration/sample-weighted history, not raw item count, when possible
round aggressively: about 7m remaining
hide ETA after failures, skips, cancellation, or denominator changes
never display exact-looking ETA such as 6m 43s remaining

Good examples:

Converting track 2 of 5: Flamenco Sketches · about 7m remaining
Extracting archive · about 1m remaining

Bad examples:

Converting track 1 of 5 · 6m 43s remaining
7. Add confidence labeling

The system should know whether progress is measured, estimated, or unknown.

User-visible wording can carry this without a large UI redesign:

Measured:
Converting track 2 of 5: So What · 67% of current track

Estimated:
Converting track 2 of 5: So What · estimating from track durations

Unknown:
Converting track 1 of 1: So What · progress unavailable from sox

Internally, this should be typed rather than inferred from message strings.

8. Add immediate cancellation progress

V1 can preserve final cancelled progress. V2 should show cancellation as soon as the user requests it:

Cancelling conversion…
Stopping sox…
Cancelled at 37%

This likely requires work near the child-process controller, not only in BroadcastReporter.

Key behavior:

cancellation request emits immediately
child-process termination can continue in the background of the current async operation
final cancellation preserves last-known progress
no jump to 100%
9. Upgrade the TUI display model

V1 should route ProgressUpdate correctly. V2 should consider display changes such as:

Overall: 42%
Current track: 67%
Converting track 2 of 5: So What · elapsed 2m 14s

This may require changing app-side message/state types, but it should not force changes to the locked pipeline contracts unless the team chooses that direction.

A backward-compatible path:

keep ProgressUpdate
continue using ConversionStatus::Processing
use existing file_progress for current-file/current-track progress
add app/TUI state fields only where needed

Acceptance criteria for v2

A v2 patch is ready when these are true:

Long single-track work never appears frozen.
Opaque operations say still running or progress unavailable.
Tool progress appears when measured data exists.
The UI distinguishes overall progress from current-file/current-track progress.
Failed/cancelled jobs preserve the point where work stopped.
ETA appears only when it has enough signal.
Progress updates do not flood the TUI.
The design remains shared across SACD, CUE, 7z, FLAC batches, and future routes.
